# Project memory: Monitoring Engineering

## Purpose and stack

Equipment monitoring web app for Interbat. Technicians record machine readings by shift and round; admins configure machines, parameters, schedules, users, and report recipients. Built with React 18, TypeScript, Vite, Tailwind CSS, Supabase (Auth, Postgres/PostgREST, Storage, Edge Functions), and jsPDF/autotable for reports.

## Main user flows

- `src/App.tsx` gates the app on Supabase authentication, profile existence, and active status; admins get extra routes.
- `src/components/Layout.tsx` provides navigation.
- Technician pages: dashboard, new monitoring, history, reports, parameter trends, and work requests (titipan pekerjaan).
- Admin pages: machines, parameters, schedules, users, report email recipients, and audit trail.
- Admin-only `Machine For Holiday (MFD)` page lists only machines whose `machine_category` is `mfd`; the category is selected on machine create/edit and existing machines default to `rutin`. Active status uses `machines.is_active` for both categories; individual toggles are on Machines, while Routine and MFD pages provide category-wide bulk activation. Category migration: `20261103100000_add_machine_category.sql`.
- Admin-only `Machine Rutin` page filters to `machine_category = 'rutin'`, and its individual/bulk activation uses the regular `machines.is_active` field. Machine list columns can be sorted in either direction.
- Titipan Pekerjaan can be deleted by its owner or an admin. Admins have a delete action directly in each list row; photo and record deletion errors are surfaced in the page.
- Titipan Pekerjaan is scheduled by date/shift/round; new requests start pending, display as in progress once their scheduled start arrives, and can be edited by authenticated technicians/admins. Completion requires details plus at least one evidence photo. The page has status summary filters, completion-date filters, and sorting. A global bell reminds users about pending tasks due now or within one hour. Monitoring PDFs (manual and emailed) exclude work requests. Migration: `20261103110000_schedule_work_requests.sql`.
- Admins manage scheduled `announcements` with message and local publish/end date-times in `AdminAnnouncements`; the newest active announcement inside its time window is shown above Dashboard stats. Its heading blinks (respects reduced-motion settings), message and timestamps remain static. Migrations: `20261106090000_announcements.sql`, `20261106100000_announcement_end_at.sql`.
- Monitoring parameters configured with `photo_required` now offer direct camera capture (rear camera hint on mobile) alongside gallery selection; each option feeds the same image-size/type validation and photo upload flow.
- `App.tsx` stores internal `PageKey` navigation in browser history state; device/browser Back and Forward now move between app pages without reloading.
- Newly registered machines are created inactive (`is_active = false`) and must be activated manually.
- `src/lib/AuthContext.tsx` maps usernames to `<normalized_username>@monitor.local`, supports sign-in and edge-function account creation, writes auth audit events, and signs out after five idle minutes.
- `src/lib/types.ts` contains core domain types and shift/round helpers. Shifts are 07–15, 15–23, and 23–07; each has two four-hour rounds. Numeric readings are classified normal/warning/abnormal against configured bounds, with 10% warning tolerance.
- `src/pages/NewMonitoring.tsx` handles scheduled parameter entry, conditional parameters, reading validation, photos, and round saving/editing. Parameters can require photos or enforce increasing cumulative values.
- Reports/history use stored round values and photos; PDF generators are in `src/lib/*PdfReport.ts` and `src/lib/pdfReport.ts`. The shift email report is generated by `supabase/functions/send-shift-report/index.ts`.

## Data model and backend

Supabase migrations in `supabase/migrations/` define profiles/roles, machines and machine parameters, parameters, schedules and scheduled parameters, monitoring rounds/values/photos, report recipients, work requests/photos, audit logs, and round conclusions. Photos use the public `monitoring-photos` bucket. RLS policies and audit triggers are defined in SQL migrations; edge functions include create-user, delete-user, and send-shift-report.

Important business constraints recorded in migrations and `README_PERUBAHAN.txt`: a machine/date/shift/round cannot be duplicated; an existing round is loaded for editing; monitoring is restricted to its active shift window (with DB-side protection); there is one shared conclusion per date/shift/round, not one per machine. Schedule parameters may depend on another parameter's value.

## Local proxy deployment

`README_PROXY.md` documents offline-LAN-client mode. `npm run build:proxy` runs `server/build-local-proxy.ps1`; the Node server `server/proxy-server.mjs` serves `dist/` and forwards `/rest/v1`, `/auth/v1`, `/storage/v1`, and `/functions/v1` to Supabase. `server/start-monitoring.bat` starts the proxy; default port is 8000. `.env.local-proxy` configures the upstream and should not be committed. `BACA-DULU.txt` is the quick start guide.

## Storage backend (Supabase Storage or Cloudflare R2)

All photo upload/delete/URL access goes through `src/lib/storage.ts`, so the backend can be switched without touching pages.

- `VITE_STORAGE_DRIVER=supabase` (default) uses the `monitoring-photos` Supabase bucket.
- `VITE_STORAGE_DRIVER=local` stores files on disk of the machine running the proxy, served at `/photos/*`. No extra database is needed: photo metadata stays in Supabase. Configure `STORAGE_DRIVER=local`, `STORAGE_DIR` (default `storage-data`), `STORAGE_MAX_BYTES`, `STORAGE_REQUIRE_AUTH` in `.env.local-proxy`. Guide: `server/PANDUAN-STORAGE-LOKAL.md`; copy old photos with `npm run migrate:local`.
- The `local` driver is only honored when `VITE_USE_LOCAL_PROXY=true`. On any static deploy (Cloudflare Pages) it silently falls back to Supabase Storage, so a stray `VITE_STORAGE_DRIVER=local` cannot break the hosted app.
- `VITE_STORAGE_DRIVER=r2` uses Cloudflare R2: `VITE_R2_PUBLIC_URL` for public reads and `VITE_STORAGE_API_URL` for the Worker that issues presigned PUT URLs and deletes objects.
- The Worker lives in `cloudflare/worker/` (`/upload`, `/delete`), verifies the Supabase access token, and signs R2 requests with `aws4fetch`. Migration guide: `cloudflare/README.md`.
- In local-proxy mode the client always uses origin-relative paths (`/storage-api/*`, `/photos/*`); `server/proxy-server.mjs` forwards them to `STORAGE_API_URL` and `R2_PUBLIC_URL` from `.env.local-proxy`.
- Local storage endpoints in `server/proxy-server.mjs`: `POST /storage-api/upload?path=...` (raw body), `POST /storage-api/delete` (JSON paths), `GET /photos/<path>`. Upload/delete verify the Supabase bearer token against `/auth/v1/user` unless `STORAGE_REQUIRE_AUTH=false`.
- The `send-shift-report` edge function reads photos from `R2_PUBLIC_URL` when that secret is set, otherwise from Supabase Storage.

## Two build targets (do not mix)

| Target | Command | Output | Storage |
|---|---|---|---|
| Local proxy (LAN/offline) | `npm run build:proxy` | `dist/` | `local` disk via `/photos/*` |
| Cloudflare Pages (static) | `npm run build:cloudflare` | `dist-cloudflare/` | Supabase Storage |

`build:cloudflare` forces `VITE_USE_LOCAL_PROXY=false` and `VITE_STORAGE_DRIVER=supabase`, and writes to a separate folder so it never overwrites the proxy build. On Cloudflare Pages set build command `npm run build:cloudflare`, output dir `dist-cloudflare`, and env vars `VITE_SUPABASE_URL` + `VITE_SUPABASE_ANON_KEY`.

`build:cloudflare` runs `node server/build-cloudflare.mjs` (cross-platform, works on Cloudflare's Linux build image). The old PowerShell version is still available as `npm run build:cloudflare:ps1` for Windows only — do NOT use it as the Cloudflare Pages build command (fails with `sh: powershell: not found`).

### Cloudflare Pages + foto di folder lokal server sendiri

Cloudflare Pages is static (no disk). To keep photos in `storage-data/` on your own machine, expose `server/proxy-server.mjs` publicly (e.g. Cloudflare Tunnel) and set at build time:

```
VITE_STORAGE_PUBLIC_URL=https://<public-proxy-host>          # baca foto  -> /photos/*
VITE_STORAGE_API_URL=https://<public-proxy-host>/storage-api # upload/hapus
```

When both are set, `build:cloudflare` automatically uses `VITE_STORAGE_DRIVER=local`; otherwise it falls back to `supabase`. The proxy must allow the Pages origin via `ALLOWED_ORIGIN` in `.env.local-proxy` (default `*`), and should set `STORAGE_ONLY=true` so only `/photos/*` + `/storage-api/*` are exposed publicly.

Full step-by-step guide (Cloudflare Tunnel + custom domain `woeng.my.id`): `server/PANDUAN-DOMAIN-FOTO.md`.

Helper files: `server/setup-cloudflared-tunnel.ps1` (`npm run setup:tunnel`, one-time tunnel+DNS+config setup), `server/start-foto-tunnel.bat` (`npm run start:foto`, runs proxy + tunnel), `server/cloudflared-config.example.yml`. Proxy env `STORAGE_ONLY=true` restricts public exposure to `/photos/*` + `/storage-api/*`.

Live setup (2026-11-13): tunnel `foto-woeng` id `100ede30-6795-4de0-a924-7ae6271b3e85`, hostname `monitoring.woeng.my.id` → `http://localhost:8001` (config.yml). Verified earlier: root 404, `/photos/*` serves files, CORS preflight 204 for `https://monitoreng.pages.dev`.

PowerShell 5.1 gotcha: never use `$ErrorActionPreference='Stop'` in scripts calling `cloudflared` — its stderr warnings become fatal `NativeCommandError`. Use the `Invoke-Native` helper pattern (capture `2>&1`, check `$LASTEXITCODE`). Also `?.` null-conditional is not supported in PS 5.1.

`EADDRINUSE` on port 8000 = proxy already running in another window. `npm run stop:proxy` (`server/stop-proxy.bat`) kills the listener using the `PORT` from `.env.local-proxy`. `proxy-server.mjs` now has a friendly `server.on('error')` handler for EADDRINUSE/EACCES plus SIGINT/SIGTERM graceful shutdown.

Proxy modes (`server/proxy-server.mjs`):
- CLI flags override `.env.local-proxy`: `--port=<n>`, `--role=app|foto|static`, `--upstream=<url>`, `--no-upstream`. Enables running two instances from one env file.
- `APP_UPSTREAM_URL` set → BRIDGE mode: all non-storage paths proxied to that upstream (e.g. `https://monitoreng.pages.dev`), photos still served from `storage-data/`. Overrides `STORAGE_ONLY`.
- `BRIDGE_REWRITE` (comma list, default `SUPABASE_URL`) → literal absolute URLs in proxied JS/HTML/CSS are rewritten to `window.location.origin` (+ path), so LAN clients never need direct internet. Regex matches quoted absolute URLs.
- Otherwise `STORAGE_ONLY=true` → only `/photos/*` + `/storage-api/*`; else STATIC mode serves `dist/`.
- `forwardTo(req,res,baseUrl,path)` is the generic upstream forwarder (also used by `/storage-api` and r2 `/photos`).

Two-port layout (current): `APP_PORT=8000` (`--role=app`, bridge, LAN only) and `TUNNEL_PORT=8001` (`--role=foto`, storage-only, exposed via Cloudflare Tunnel). `%USERPROFILE%\.cloudflared\config.yml` ingress → `http://localhost:8001`. `server/start-foto-tunnel.bat` launches all three windows; `server/stop-proxy.bat` kills both ports.

Note: a separate Windows service `Cloudflared` (LocalSystem, `tunnel run --token-file C:\ProgramData\cloudflared\token`) also runs — unrelated to tunnel `foto-woeng`; do not kill it.

Verified 2026-11-13: 8000 root 200 (app HTML), 8001 root 404, `/photos/_uji/t.png` 200 on 8000/8001/public, `https://monitoring.woeng.my.id/` 404.
